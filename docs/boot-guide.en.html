Booting Linux 0.11: from power-on to the shell

From the moment the BIOS loads the boot sector, through main(), to the shell prompt [/usr/root]#, following this repository's source. The kernel source is Linus' original (linux-0.11-original/) with only what gcc 4.8 and QEMU strictly need changed; bootsect.s and setup.s are identical to the original. The changes are listed in the README under "Changes from the original" and in Q7 below. Addresses and values were checked with gdb in QEMU (-m 16M).

In short

  • The boot loader is two programs, bootsect + setup. jmpi 0,8 in setup.s (line 193) is the border between boot loader and kernel.
  • Loading from disk into RAM is finished first, in real mode, because the BIOS disk interrupt (int 0x13) works only in real mode.
  • Then setup turns on protected mode, and the 32-bit kernel starts at startup_32 in head.s (address 0) and reaches main().
  • init (task 1), created by main(), mounts the root file system from the hard disk and starts /bin/sh. From the root mount on, the kernel uses its own driver (hd.c).
  • Machine code carries no 16/32-bit marker. How it is read depends on the CPU's current mode and the assembler/disassembler settings.

2. Step by step to the shell

Locations are file:line in the source, relative to the repository root. The numbers are the actual order of execution. Black boxes are what that step prints on screen.

  1. CPU reset, BIOS

    real modeSeaBIOS ROM · 0xF0000~0xFFFFF

    Right after reset the CPU starts at f000:fff0 (linear 0xFFFF0). The jmp f000:e05b there enters the BIOS, which runs the power-on self test (POST), fills the interrupt vector table and BIOS data area, and runs the VGA BIOS and the iPXE option ROM.

    screenSeaBIOS (version 1.16.3-...) iPXE (https://ipxe.org) ... Booting from Floppy...
    gdb: right after attaching, info registers cs eip → cs=0xf000 eip=0xfff0

  2. The BIOS loads the boot sector at 0x7c00

    real modeboot/bootsect.s:252–253

    It reads the first 512 bytes of the floppy (the start of Image = bootsect) to 0x7c00. If the last two bytes are 0x55 0xAA (boot_flag: .word 0xAA55), the sector is bootable and the BIOS jumps to 0000:7c00.

    gdb: stops at hbreak *0x7c00. x/2xb 0x7dfe → 0x55 0xaa

  3. bootsect copies itself to 0x90000

    real modebootsect.s:46–56

    The area around 0x7c00 is about to be reused, so mov cx,#256 + rep movw moves 256 words (512 bytes) to 0x9000:0000, and jmpi go,INITSEG continues in the copy.

    gdb: hbreak *0x90018 (go:)

  4. Stack, then read setup

    real modego:57 · load_setup:67

    ds=es=ss=0x9000, sp=0xFF00 (stack at 0x9FF00). BIOS int 0x13 (AH=2) reads SETUPLEN=4 sectors, starting at sector 2, to 0x90200. On failure it resets the disk (AH=0) and retries.

  5. Disk parameters and the message

    real modeok_load_setup:79 · int 0x10:96,102

    int 0x13 (AH=8) returns the sectors per track, stored in sectors (18 for a 1.44 MB floppy). Then int 0x10 (AH=3 cursor position, AX=0x1301 write string) prints msg1, the only message the original boot loader prints.

    screenLoading system ...
    gdb: hbreak *0x9003d (ok_load_setup:)

  6. Read system (the kernel) to 0x10000

    real modecall read_it:109 · read_it:151 · read_track:198

    With es=SYSSEG (0x1000), read_it repeats int 0x13 track by track up to ENDSEG (0x4000, i.e. 0x40000): at most SYSSIZE=0x3000 paragraphs = 192 KB. This kernel is about 107 KB. It is the longest part to follow with si (one int 0x13 runs tens of thousands of BIOS instructions).

    gdb: to skip it, hbreak *0x9006c → continue

  7. Motor off, root device, jump to setup

    real modekill_motor:110 · root_defined:131 · jmpi:139

    Stops the floppy motor (kill_motor) and checks root_dev at byte 508. ROOT_DEV = 0x306 in the source is overwritten at build time: tools/build.c reads the device number of ROOT_DEV=/dev/hd1 and writes 0x0301 (hd1, partition 1 of the first hard disk). If it is 0, the floppy type is chosen from the sector count (15→0x208, 18→0x21c). Finally jmpi 0,SETUPSEG (cs=0x9020) hands over to setup.

    This is all of disk → RAM loading, possible because we are still in real mode with the BIOS. gdb: x/1xh 0x901fc → 0x0301

  8. setup collects hardware information

    real modeboot/setup.s:31–105

    The last step that uses the BIOS. It reads int 0x10 (cursor position, video mode, EGA info), int 0x15 AH=0x88 (extended memory above 1 MB, in KB), the hard disk parameter tables pointed to by the int 0x41/0x46 vectors, and int 0x13 AH=0x15 (is there a second disk), and stores them at 0x90000~0x901FF, where bootsect used to be. See the table in the memory map.

    gdb: hbreak *0x90200. It shows SIGTRAP instead of Breakpoint; that is expected

  9. setup moves system to 0x0

    real modecli:109 · do_move:115 · end_move:130

    First cli disables interrupts. do_move copies 0x10000~0x8FFFF to 0x0, 64 KB (cx=0x8000 words) at a time. This overwrites the BIOS interrupt vector table (0x0~0x3FF), so no BIOS call is possible afterwards.

    gdb: at the start of setup, x/4xb 0x0 → 53 ff 00 f0 (IVT, int 0 = f000:ff53). At startup_32 it reads b8 10 00 00 (mov $0x10,%eax, kernel code)

  10. setup prepares protected mode

    real modelidt:133 · lgdt:134 · A20:139–142 · 8259:154–

    ① lidt loads an empty IDT (limit 0) and lgdt a temporary GDT (null, code 0x08, data 0x10); code and data both have base=0, limit=8 MB, 32-bit (gdt:205). ② 0xD1 and 0xDF sent to the 8042 keyboard controller turn on A20, so addresses above 1 MB work. ③ The 8259A PICs are reprogrammed to put hardware interrupts at 0x20~0x2F (clear of CPU exceptions 0~0x1F), all masked for now.

  11. Turn on PE and far-jump

    →protected modesetup.s:192 · :193

    mov ax,#0x0001 + lmsw ax (a 286 instruction writing the low 16 bits of CR0, PE=1), immediately followed by jmpi 0,8. The far jump reloads CS from the GDT code descriptor (selector 0x08) and flushes the prefetch queue. From that moment the CPU reads the same bytes as 32-bit code and runs EIP=0, i.e. startup_32. The boot loader's job ends here.

    gdb: hbreak *0x90301 (lmsw), hbreak *0x90304 (jmpi). Between the two PE is 1 but CS still holds the real-mode value (0x9020), so the code is still 16-bit. That is why d16 checks CS as well.

  12. head: startup_32 sets up the kernel environment

    protected modeboot/head.s:17–48

    ds/es/fs/gs=0x10 (data selector); lss _stack_start,%esp puts the stack at the end of user_stack (kernel/sched.c); setup_idt points all 256 vectors at ignore_int (which prints Unknown interrupt); setup_gdt installs the kernel's GDT. Then it checks that A20 is really on (if a value written at 0x000000 shows up at 0x100000, it is not; lines 33–36) and whether an x87 coprocessor exists (check_x87:54).

    gdb: hbreak *0x0. When it stops, d16 switches to 32-bit and the tools/system symbols by itself

  13. head: paging on, ret into main

    protected modeafter_page_tables:135 · setup_paging:198–219

    after_page_tables pushes main's three arguments (0), the return address L6, and the address of main. setup_paging maps 0~16 MB 1:1 with pg0~pg3 (0x1000~0x4FFF), loads the page directory (pg_dir, address 0) into cr3 and sets CR0.PG. The final ret jumps to the main address on the stack. It uses ret rather than jmp main to flush the prefetch queue right after enabling paging (source comment: this also flushes prefetch-queue).

    The page tables are filled backwards with std (fill pages backwards). The original then enters main with the direction flag (DF) still set; this repository adds one cld right after (head.s:213), because gcc 4.8 code assumes DF=0 (Q7).

  14. main(): kernel initialisation

    protected modeinit/main.c:104–149

    Reads what setup left at 0x901FC (root device), 0x90080 (disk info) and 0x90002 (extended memory) to size memory; with 16 MB, memory_end=0xFE0000 and the buffer cache goes up to 4 MB. Then mem_init → trap_init → blk_dev_init → chr_dev_init → tty_init → time_init → sched_init → buffer_init → hd_init → floppy_init, and sti() (136) enables interrupts. move_to_user_mode() (137) drops task 0 to user mode, and after fork the child (task 1) runs init(). Task 0 stays in for(;;) pause();.

    fork() and pause() must be inlined into main, not called (main.c comment: so that there won't be any messing with the stack from main()). A fork from kernel space gets no copy-on-write until execve, so task 0 and task 1 share the stack (comment at main.c lines 10–16); a function call from main after fork would overwrite it and break the child. The original Makefile's -O does the inlining, and the disassembly confirms both int $0x80 are inside main.

    gdb: hbreak main → main () at init/main.c:105

  15. init: read the hard disk partitions

    protected modemain.c:172 setup() → kernel/blk_drv/hd.c:73 sys_setup

    init() calls the setup() system call; the kernel's sys_setup configures the drives from the disk info setup.s saved and reads the partition table with the kernel's own driver (hd.c). From here on the kernel, not the BIOS, reads the disk.

    The original soft-resets the IDE controller on the first request and waits for the READY bit of the status register before sending a command. In QEMU, SeaBIOS leaves the (absent) slave selected, so the status reads 0x00, and READY is not set after the reset either: the kernel panics with HD controller not ready. This repository therefore skips the reset at boot (reset = 0) and waits only for BUSY to clear: two lines.

    screenPartition table ok.
    Without the hard disk image this fails with harddisk I/O error. gdb: hbreak sys_setup

  16. init: mount the root file system

    protected modehd.c:159 → fs/super.c:242 mount_root

    Reads the superblock of ROOT_DEV (0x0301), mounts it as root, and counts the free blocks and inodes. On failure it stops with panic("Unable to mount root") (super.c:262).

    screen46081/60000 free blocks 19232/20000 free inodes

  17. init: open the console, print memory info

    protected modeinit/main.c:173–178

    Opens /dev/tty0 as standard input/output/error (0, 1, 2) and prints the buffer cache and free main memory. This is not printk but a user-mode printf → write system call. Free mem = 0xFE0000 − 0x400000 = 12451840.

    screen3466 buffers = 3549184 bytes buffer space Free mem: 12451840 bytes

  18. Run /etc/rc

    program on the disk imagemain.c:179–187 → /etc/rc in hdc-0.11.img

    A forked child redirects standard input to /etc/rc and runs /bin/sh. /etc/rc is a script on the disk image, not kernel source: /etc/update &, echo "/dev/hd1 /" > /etc/mtab, echo " Ok. ".

    screen Ok.

  19. Login shell

    program on the disk imagemain.c:189–207

    init loops forever: fork → setsid → open /dev/tty0 → execve("/bin/sh") (HOME=/usr/root). When the shell exits it prints child N died with code ... and starts another.

    screen[/usr/root]# _

The 1 MB real-mode space and the BIOS

Real mode can address only 1 MB (0x00000~0xFFFFF). The BIOS uses the very bottom (IVT, BDA), just below 640 KB (EBDA) and above 640 KB (ROMs). In short: system BIOS code at 0xF0000~0xFFFFF (64 KB), VGA BIOS at 0xC0000~0xCAFFF, BIOS data at 0x0~0x4FF and 0x9FC00~0x9FFFF.

Segment:offset

The linear address in real mode is cs*16 + ip. gdb's $pc shows only ip, so it looks small, like 0x104.

Example: 9020:0104 → 0x90200 + 0x104 = 0x90304, the real address of setup's jmpi 0,8.

BIOS interrupts and loading

Disk reads (int 0x13) are provided by the BIOS for real mode. Protected mode cannot call BIOS code as it is, so loading must be done before the switch. After the switch, the kernel's hd.c and floppy.c access the disks.

GDT and selectors

In protected mode, values like cs and ds are not addresses but GDT entry numbers. setup's GDT has three entries: null (0x00), code (0x08), data (0x10), both with base=0, limit=8 MB, 32-bit. So linear address = offset, which keeps things simple. The 8 in jmpi 0,8 is the code selector.

The PE bit and the far jump

Setting CR0.PE starts protected mode, but CS keeps its cached value. A far jump reloads CS with the new selector so the 32-bit code segment takes effect. That is why jmpi comes right after lmsw ax. The original uses the 286-era lmsw (write the low 16 bits of CR0) rather than mov cr0,eax.

A20 and the PIC

A20: the 21st address line, held low for 8086 compatibility. Unless it is enabled, memory above 1 MB wraps around to 0. The original enables it through the 8042 keyboard controller. PIC reprogramming: moves IRQ numbers to 0x20 and up so they do not collide with CPU exception numbers.

Paging (in head)

Four page tables, pg0~pg3, map 0~16 MB 1:1 (virtual = physical). Loading pg_dir (address 0) into cr3 and setting CR0.PG turns paging on. The page directory sits at address 0 because it reuses the place of head's early code, which is no longer needed.

Why two assemblers

bootsect.s and setup.s are the 1991 originals in as86 syntax (mov ax,#BOOTSEG, ! comments), assembled with as86 -0 (8086, 16-bit). ld86 produces files with a 32-byte minix header; the original tools/build.c strips it and concatenates bootsect (512 B) + setup (4 sectors) + system into Image. The kernel side (head.s, system_call.s, ...) is assembled by GNU as (AT&T syntax, as --32) into 32-bit ELF. The original Linux 0.11 was organised the same way (with a.out instead of ELF). a.out C symbols carried a leading _ (main → _main), so the original .s files refer to _main, _schedule, ... Today gcc gets -fleading-underscore to produce the same names, and the original .s files are used unchanged. Thanks to the debug info, gdb takes the names without _ (hbreak main).

Assembly and machine code

16/32-bit is an instruction to the assembler and leaves no trace in the binary. The same mov ax,#0x07c0 is B8 C0 07 in 16-bit code and 66 B8 C0 07 in 32-bit code (0x66 is the prefix that flips the operand size). The CPU sees only bytes; the current mode decides how they are read. If the assembler setting and the CPU's actual mode disagree, instruction lengths differ, every following byte is misread, and it fails silently, without any error.

6. Questions and answers

Questions that came up while working on this.

Q1. When d16 decodes, how does it tell machine code from assembly?

It does not. Machine code carries no mode marker, and assembly is gone once assembled. d16 is not kernel code but a debugging command that runs inside gdb (scripts/d16.py).

  • It reads the bytes at the current position from QEMU's memory and disassembles them as 16-bit with objdump -m i8086.
  • The detour is needed because gdb decodes x/i as 32-bit even after set architecture i8086. A layout asm full of add BYTE PTR [eax],al is the symptom.
  • The mode is chosen from the CPU state (CR0.PE and CS), automatically.
Q2. I cannot tell where in the source the current instruction is.

output/bootsect.elf only wraps the finished binary in ELF, so it has no debug info (line table); gdb shows just in ?? ().

Instead, the listings made by as86 -l (output/bootsect.lst, output/setup.lst) map line / offset / machine code / source one to one. Addresses follow the table below; d16 applies it automatically and appends lines like ; bootsect.s:47 mov ax,#BOOTSEG.

bootsect (before moving)0x7c00 + offsetloaded by the BIOS
bootsect (after moving)0x90000 + offsetjmpi go,INITSEG (bootsect.s:56)
setup0x90200 + offset (cs=0x9020)jmpi 0,SETUPSEG (bootsect.s:139)

Q3. After the switch to protected mode the code is 32-bit, so d16 would be wrong. How do I check it?

That is why d16 treats CR0.PE=1 with CS holding a GDT selector (a small value) as protected mode, switches with set architecture i386 and symbol-file tools/system, and uses plain x/i. Just pressing stepi follows the switch.

Why CS too: between lmsw ax and jmpi 0,8, PE is 1 but CS still holds the real-mode value, so the code is still 16-bit. After the switch, list shows lines of head.s and main.c.

Q4. Does the boot loader enter protected mode? Is the OS loaded into RAM after that?

Entering protected mode is indeed the boot loader's (setup's) last job, but the order is the other way round: loading from disk into RAM comes first, done in real mode with the BIOS; then setup switches modes.

  • The boot loader is bootsect + setup. Its job: "load the kernel into RAM, turn on protected mode, jump to the entry point".
  • From head.s on it is the kernel (system). The single line jmpi 0,8 is the border.
  • Disk access after protected mode (the root file system, ...) is done by kernel drivers.
Q5. I got tired of si, used continue, and got Kernel panic: Unable to mount root. Did it never leave the boot loader?

No. If kernel messages appear after Loading system ..., it went through bootsect → setup → head → main. The hard disk image with the root file system was not attached to QEMU, so it stopped at the root mount (step 16 above). scripts/qemu-debug.sh boot now attaches output/hdc-0.11.img when it exists, so continue reaches the shell.

continue runs to the next breakpoint, so it is fine to use. Instead of si 50000, put an hbreak where you want to look and continue (table below).

Q6. VSCode works down to main; why not for the boot loader?

In the boot sector, VSCode (cppdbg) reads gdb's stopped state as "running", so stepi does not work. Debug with two WSL terminals instead (4_debug_qemu.sh: QEMU, 5_debug_gdb.sh: gdb). From protected mode on (startup_32~main) the VSCode configuration works.

Q7. Why does the original source not build as it is? What was changed?

The original targets gcc 1.x and a.out (1991); the build environment (Ubuntu 14.04) has only gcc 4.8. Nothing was changed for optimization: only what is strictly needed to build with today's compiler and run correctly. 26 files differ from the original; diff -r linux-0.11-original . -x linux-0.11-original -x .git shows them all.

  • Compile errors: inline asm listing an input register as clobbered (impossible constraints since gcc 3), a cast used as an lvalue, a bare #elif, xorl %al,%al, .align 3 (2³ bytes in a.out, 3 bytes in ELF), "r" constraints on byte values (giving %sil).
  • No error, wrong behaviour: gcc 4.8 assumes "DF=0 at function boundaries" and compiles struct copies to rep movsl. The original leaves DF set after std, so fork's *p = *current right after get_free_page() copied backwards. Task 1's priority became 0 and the scheduler never picked init. Fixed by a cld at the end of the four places that use std.
  • a.out symbols: the original .s files call C symbols _main and so on. Instead of editing them, gcc gets -fleading-underscore.
  • Environment: QEMU IDE compatibility (two lines in hd.c, see step 15), a case-insensitive Windows drive (the keyboard.S build rule), and compile options (-m32) plus Makefile glue to use the original build.c unchanged.
Q8. The kernel went from 127 KB to 107 KB. Does it behave differently?

No. The earlier version lacked -O (optimization) in its compile options; this one uses -O as the original Makefile does. The same C code compiled at the original's optimization level is simply smaller. -O is also what inlines fork/pause (step 14).

On the other hand, gdb may show some variables as <optimized out>, and next may jump back and forth between lines. That is normal for optimized code.

Q9. Why was the keyboard layout changed?

The original default is Finnish (KBD_FINNISH in include/linux/config.h), so typing on a US/Korean keyboard into the QEMU shell gives - for /, + for - and : for >. KBD_US, already in the original, is enabled and KBD_FINNISH disabled. keyboard.S assembles only the enabled table, so the kernel size is the same; with both enabled, Finnish wins because it is tested first.

7. Checking with gdb

Run from the repository root. Once, build the Image and listings with ./2_build.sh.

# Terminal 1: QEMU waiting for gdb (output/Image + output/hdc-0.11.img); the QEMU window opens too
./4_debug_qemu.sh

# Terminal 2: gdb; stops at 0x7c00 and prints the current instruction and source line at every stop
./5_debug_gdb.sh
BreakpointWhere (original source)
hbreak *0x7c00bootsect start (set by terminal 2)
hbreak *0x90018go: (right after bootsect moved itself to 0x90000)
hbreak *0x9003dok_load_setup: (the four setup sectors were read)
hbreak *0x9006ccall kill_motor (kernel loaded; skips the longest part)
hbreak *0x90093jmpi 0,SETUPSEG (jump to setup)
hbreak *0x90200setup start
hbreak *0x90301 / *0x90304lmsw ax / jmpi 0,8
hbreak *0x0startup_32 (head.s)
hbreak maininit/main.c:105 (once the symbols are loaded after the switch)
hbreak sys_setup / printk / panicstart of the root mount / kernel messages / kernel panic

Addresses are the offset (second column) in output/*.lst plus the load address. They move when the source changes, so look them up in the listing again.

To seeHow

Memory after loadingx/16xb 0x10000 (before the move), x/16xb 0x0 (after)
QEMU's memory mapmonitor info mtree -f
Finishquit in gdb → Ctrl+C in terminal 1; kill a leftover QEMU with pkill -f '^qemu-system-i386'

In setup (cs=0x9020) gdb takes $pc to be ip (e.g. 0x104), so a stop at an hbreak on a linear address shows Program received signal SIGTRAP instead of Breakpoint N. That is expected.

Written against this repository's boot/bootsect.s, boot/setup.s (identical to Linus' original), boot/head.s, init/main.c, kernel/blk_drv/hd.c (original + minimal gcc 4.8/QEMU patches) and scripts/d16.py. Addresses and values were checked in QEMU -m 16M. Line numbers and addresses change when the source changes.
