Linux 0.11 부팅: 전원이 켜지고 쉘이 뜨기까지

BIOS가 부트섹터를 올리는 순간부터 main()을 거쳐 쉘 프롬프트 [/usr/root]#가 뜨기까지, 이 저장소의 소스 기준으로 정리했습니다. 커널 소스는 Linus의 원본(linux-0.11-original/)에 gcc 4.8로 빌드하고 QEMU로 부팅하는 데 꼭 필요한 것만 고친 것이고, bootsect.s·setup.s는 원본과 같습니다. 고친 내용은 README의 "원본과 다른 점"과 아래 Q7에 있습니다. 주소와 값은 QEMU(-m 16M)에서 gdb로 실제로 확인한 것입니다.

한 줄 요약

  • 부트로더는 bootsect + setup 두 개이고, setup.s의 jmpi 0,8(193번째 줄)이 부트로더와 커널의 경계입니다.
  • 디스크에서 RAM으로 올리는 일은 리얼모드에서 먼저 끝냅니다. BIOS 디스크 인터럽트(int 0x13)가 리얼모드 전용이기 때문입니다.
  • 그 다음 setup이 보호모드를 켜고, head.s의 startup_32(0번지)부터 32비트 커널이 시작해 main()에 도달합니다.
  • main()이 만든 init(task 1)이 하드디스크의 루트 파일시스템을 마운트하고 /bin/sh를 띄웁니다. 루트 마운트부터는 커널 자신의 드라이버(hd.c)로 합니다.
  • 기계어에는 16/32비트 표시가 없습니다. 어느 쪽으로 읽을지는 CPU의 현재 모드와 어셈블러/디스어셈블러 설정이 정합니다.

1. 전체 구상도

색은 CPU 모드입니다. 리얼모드 16비트 보호모드 32비트

2. 쉘까지의 과정, 단계별

위치는 저장소 루트 기준 소스의 파일:줄 번호입니다. 번호는 실제 실행 순서입니다. 검은 상자는 그 단계에서 화면에 찍히는 메시지입니다.

  1. CPU 리셋, BIOS 실행

    리얼모드SeaBIOS ROM · 0xF0000~0xFFFFF

    CPU는 리셋 직후 f000:fff0(선형 0xFFFF0)에서 시작합니다. 거기 있는 jmp f000:e05b로 BIOS 본체에 들어가 하드웨어 점검(POST), 인터럽트 벡터 테이블·BIOS 데이터 영역 채우기, VGA BIOS와 iPXE 옵션 ROM 실행을 합니다.

    화면SeaBIOS (version 1.16.3-...) iPXE (https://ipxe.org) ... Booting from Floppy...
    gdb: 접속 직후 info registers cs eip → cs=0xf000 eip=0xfff0

  2. BIOS가 부트섹터를 0x7c00에 올린다

    리얼모드boot/bootsect.s:252–253

    플로피의 첫 512바이트(Image의 맨 앞 = bootsect)를 0x7c00에 읽고, 마지막 2바이트가 0x55 0xAA(boot_flag: .word 0xAA55)이면 부팅 가능한 섹터로 보고 0000:7c00으로 점프합니다.

    gdb: hbreak *0x7c00 에서 멈춤. x/2xb 0x7dfe → 0x55 0xaa

  3. bootsect가 자기 자신을 0x90000으로 복사한다

    리얼모드bootsect.s:46–56

    0x7c00 근처는 곧 다른 용도로 써야 하므로, mov cx,#256 + rep movw로 256워드(512바이트)를 0x9000:0000으로 옮기고 jmpi go,INITSEG로 복사본에서 계속 실행합니다.

    gdb: hbreak *0x90018 (go:)

  4. 스택을 잡고 setup을 읽는다

    리얼모드go:57 · load_setup:67

    ds=es=ss=0x9000, sp=0xFF00(스택 = 0x9FF00). BIOS int 0x13(AH=2)로 2번 섹터부터 SETUPLEN=4섹터를 0x90200에 읽습니다. 실패하면 디스크를 리셋(AH=0)하고 다시 읽습니다.

  5. 디스크 정보를 얻고 메시지를 찍는다

    리얼모드ok_load_setup:79 · int 0x10:96,102

    int 0x13(AH=8)로 트랙당 섹터 수를 얻어 sectors에 저장합니다(1.44MB 플로피 = 18). 이어서 int 0x10(AH=3 커서 위치, AX=0x1301 문자열 출력)으로 msg1을 찍습니다. 원본 부트로더가 화면에 쓰는 유일한 메시지입니다.

    화면Loading system ...
    gdb: hbreak *0x9003d (ok_load_setup:)

  6. system(커널)을 0x10000에 읽는다

    리얼모드call read_it:109 · read_it:151 · read_track:198

    es=SYSSEG(0x1000)로 두고 read_it이 ENDSEG(0x4000, 즉 0x40000)까지 트랙 단위로 int 0x13을 반복합니다. 최대 SYSSIZE=0x3000 단락=192KB. 지금 커널은 약 107KB입니다. 부팅에서 si로 따라가기 가장 긴 구간입니다(int 0x13 하나 안에서 BIOS 코드가 수만 개 실행됨).

    gdb: 이 구간은 건너뛰려면 hbreak *0x9006c → continue

  7. 모터를 끄고 루트 장치를 정한 뒤 setup으로 점프

    리얼모드kill_motor:110 · root_defined:131 · jmpi:139

    플로피 모터를 끄고(kill_motor), 508번째 바이트의 root_dev를 확인합니다. 소스의 ROOT_DEV = 0x306은 빌드할 때 tools/build.c가 ROOT_DEV=/dev/hd1 장치 번호를 읽어 0x0301(hd1, 첫 하드디스크의 1번 파티션)로 덮어씁니다. 0이면 섹터 수로 플로피 종류를 골라(15→0x208, 18→0x21c) 정합니다. 마지막으로 jmpi 0,SETUPSEG(cs=0x9020)로 setup에 넘깁니다.

    여기까지가 디스크 → RAM 적재의 전부입니다. 아직 리얼모드이고 BIOS를 쓸 수 있어서 가능합니다. gdb: x/1xh 0x901fc → 0x0301

  8. setup이 하드웨어 정보를 수집한다

    리얼모드boot/setup.s:31–105

    BIOS를 쓰는 마지막 단계입니다. int 0x10(커서 위치·비디오 모드·EGA 정보), int 0x15 AH=0x88(1MB 이후 확장 메모리 KB), int 0x41/0x46 벡터가 가리키는 하드디스크 파라미터 표, int 0x13 AH=0x15(두 번째 디스크 유무)를 읽어 bootsect가 있던 0x90000~0x901FF에 저장합니다. 자세한 위치는 메모리 맵의 표를 보세요.

    gdb: hbreak *0x90200. 멈추면 Breakpoint 대신 SIGTRAP으로 표시되는 게 정상

  9. setup이 system을 0x0으로 옮긴다

    리얼모드cli:109 · do_move:115 · end_move:130

    먼저 cli로 인터럽트를 끕니다. do_move가 0x10000~0x8FFFF를 64KB(cx=0x8000 워드)씩 0x0으로 복사합니다. 이 복사가 BIOS 인터럽트 벡터 테이블(0x0~0x3FF)을 덮으므로, 이후로는 BIOS 호출이 불가능합니다.

    gdb: setup 시작에서 x/4xb 0x0 → 53 ff 00 f0(IVT, int 0 = f000:ff53). startup_32에서 다시 보면 b8 10 00 00(mov $0x10,%eax, 커널 코드)

  10. setup이 보호모드를 준비한다

    리얼모드lidt:133 · lgdt:134 · A20:139–142 · 8259:154–

    ① lidt로 비어 있는 IDT(limit 0), lgdt로 임시 GDT(널, 코드 0x08, 데이터 0x10)를 등록합니다. 코드·데이터 모두 base=0, limit=8MB, 32비트입니다(gdt:205). ② 8042 키보드 컨트롤러에 0xD1, 0xDF를 보내 A20을 켜서 1MB 위 주소를 쓸 수 있게 합니다. ③ 8259A PIC를 다시 설정해 하드웨어 인터럽트를 0x20~0x2F번으로 옮기고 일단 전부 막습니다(CPU 예외 0~0x1F와 겹치지 않도록).

  11. PE를 켜고 far jump로 넘어간다

    →보호모드setup.s:192 · :193

    mov ax,#0x0001 + lmsw ax(CR0의 하위 16비트에 쓰는 286 명령, PE=1) 직후 jmpi 0,8. far jump는 CS를 GDT의 코드 디스크립터(셀렉터 0x08)로 다시 읽고 명령 프리페치를 비웁니다. 그 순간부터 CPU는 같은 바이트를 32비트로 해석하고, EIP=0, 즉 startup_32를 실행합니다. 부트로더의 일은 여기서 끝납니다.

    gdb: hbreak *0x90301(lmsw), hbreak *0x90304(jmpi). PE=1과 jmpi 사이는 PE=1이지만 CS가 아직 리얼모드 값(0x9020)이라 여전히 16비트입니다. d16이 CS까지 보고 판별하는 이유입니다.

  12. head: startup_32가 커널 환경을 만든다

    보호모드boot/head.s:17–48

    ds/es/fs/gs=0x10(데이터 셀렉터), lss _stack_start,%esp로 스택을 user_stack(kernel/sched.c) 끝에 잡고, setup_idt(256개 벡터를 모두 ignore_int로. 처리 안 된 인터럽트가 오면 Unknown interrupt를 찍음), setup_gdt(커널의 GDT로 교체)를 합니다. 그 다음 A20이 정말 켜졌는지(0x000000에 쓴 값이 0x100000에 보이면 안 켜진 것, 33–36줄) 확인하고, x87 수치 보조프로세서 유무를 검사합니다(check_x87:54).

    gdb: hbreak *0x0. 멈추면 d16이 자동으로 32비트 + tools/system 심볼로 전환

  13. head: 페이징을 켜고 ret으로 main에 들어간다

    보호모드after_page_tables:135 · setup_paging:198–219

    after_page_tables가 스택에 main의 인자 3개(0), 복귀 주소 L6, 그리고 main의 주소를 쌓아 둡니다. setup_paging이 pg0~pg3(0x1000~0x4FFF)으로 0~16MB를 1:1 매핑하고, 페이지 디렉터리(pg_dir, 주소 0)를 cr3에 넣고 CR0.PG를 켭니다. 마지막 ret이 스택에 있던 main 주소로 점프합니다. jmp main이 아니라 ret을 쓰는 이유는 페이징을 켠 직후 프리페치 큐를 비우기 위해서입니다(소스 주석: this also flushes prefetch-queue).

    페이지 테이블은 std로 거꾸로 채웁니다(fill pages backwards). 원본은 그 뒤 방향 플래그(DF)를 끄지 않고 main에 들어가는데, 이 저장소는 바로 뒤에 cld를 한 줄 넣었습니다(head.s:213). gcc 4.8이 만든 코드는 DF=0을 가정하기 때문입니다(Q7).

  14. main(): 커널 초기화

    보호모드init/main.c:104–149

    setup이 남긴 0x901FC(루트 장치), 0x90080(디스크 정보), 0x90002(확장 메모리)를 읽어 메모리 범위를 정합니다. 16MB면 memory_end=0xFE0000, 버퍼 캐시는 4MB까지입니다. 이어서 mem_init → trap_init → blk_dev_init → chr_dev_init → tty_init → time_init → sched_init → buffer_init → hd_init → floppy_init 순으로 초기화하고 sti()(136)로 인터럽트를 켭니다. move_to_user_mode()(137)로 task 0을 사용자 모드로 내리고 fork하면 자식(task 1)이 init()을 실행합니다. task 0은 for(;;) pause();로 남습니다.

    fork()와 pause()는 함수 호출이 아니라 main 안에 인라인되어야 합니다(main.c 주석: so that there won't be any messing with the stack from main()). 커널 공간에서 fork하면 execve 전까지 쓰기 시 복사(copy-on-write)가 일어나지 않아 task 0과 task 1이 같은 스택을 씁니다(main.c 10–16줄 주석). fork 뒤에 main이 함수를 부르면 그 스택을 덮어써서 자식이 망가집니다. 원본 Makefile의 -O가 이 인라인을 만들어 주고, 실제로 int $0x80 두 개가 main 안에 들어간 것을 디스어셈블로 확인했습니다.

    gdb: hbreak main → main () at init/main.c:105

  15. init: 하드디스크 파티션을 읽는다

    보호모드main.c:172 setup() → kernel/blk_drv/hd.c:73 sys_setup

    init()이 setup() 시스템 콜을 부르면 커널의 sys_setup이 setup.s가 저장해 둔 디스크 정보로 드라이브를 설정하고, 커널 자신의 드라이버(hd.c)로 파티션 테이블을 읽습니다. 이제 BIOS가 아니라 커널이 디스크를 읽습니다.

    원본은 첫 요청 때 IDE 컨트롤러를 소프트 리셋하고, 명령을 보내기 전에 상태 레지스터의 READY 비트를 기다립니다. QEMU에서는 SeaBIOS가 장치 선택을 (없는) 슬레이브에 남겨 두어 상태가 0x00이고, 리셋 뒤에도 READY가 서지 않아 HD controller not ready로 panic합니다. 그래서 이 저장소는 부팅 시 리셋을 건너뛰고(reset = 0), BUSY 비트만 확인하도록 두 줄을 바꿨습니다.

    화면Partition table ok.
    하드디스크 이미지가 없으면 여기서 harddisk I/O error가 납니다. gdb: hbreak sys_setup

  16. init: 루트 파일시스템을 마운트한다

    보호모드hd.c:159 → fs/super.c:242 mount_root

    ROOT_DEV(0x0301)의 슈퍼블록을 읽어 루트로 마운트하고, 빈 블록·빈 inode 수를 세어 출력합니다. 실패하면 panic("Unable to mount root")(super.c:262)로 멈춥니다.

    화면46081/60000 free blocks 19232/20000 free inodes

  17. init: 콘솔을 열고 메모리 정보를 찍는다

    보호모드init/main.c:173–178

    /dev/tty0을 열어 표준 입출력(0, 1, 2)으로 만들고, 버퍼 캐시와 남은 주 메모리를 출력합니다. 이건 printk가 아니라 사용자 모드 printf → write 시스템 콜입니다. Free mem = 0xFE0000 − 0x400000 = 12451840.

    화면3466 buffers = 3549184 bytes buffer space Free mem: 12451840 bytes

  18. /etc/rc 실행

    디스크 이미지의 프로그램main.c:179–187 → hdc-0.11.img의 /etc/rc

    fork한 자식이 표준 입력을 /etc/rc로 바꾸고 /bin/sh를 실행합니다. /etc/rc는 커널 소스가 아니라 디스크 이미지 안의 스크립트로, /etc/update &, echo "/dev/hd1 /" > /etc/mtab, echo " Ok. "를 실행합니다.

    화면 Ok.

  19. 로그인 쉘

    디스크 이미지의 프로그램main.c:189–207

    init은 무한 루프로 fork → setsid → /dev/tty0 열기 → execve("/bin/sh")(HOME=/usr/root)를 하고, 쉘이 끝나면 child N died with code ...를 찍고 다시 띄웁니다.

    화면[/usr/root]# _

리얼모드 1MB와 BIOS 영역

리얼모드에서는 1MB(0x00000~0xFFFFF)까지만 주소를 쓸 수 있습니다. 그중 BIOS가 쓰는 곳은 맨 아래(IVT·BDA), 640KB 바로 밑(EBDA), 640KB 위쪽(ROM)입니다. 정리하면 시스템 BIOS 코드는 0xF0000~0xFFFFF(64KB), VGA BIOS는 0xC0000~0xCAFFF, BIOS가 쓰는 데이터는 0x0~0x4FF와 0x9FC00~0x9FFFF입니다.

5. 핵심 개념

위 과정을 이해하는 데 필요한 것만 추렸습니다.

리얼모드보호모드
비트 폭 기본값16비트32비트 (코드 디스크립터의 D=1일 때)
주소 계산세그먼트 × 16 + 오프셋, 최대 1MB세그먼트 레지스터는 GDT 인덱스(셀렉터), 디스크립터 base + 오프셋, 최대 4GB
BIOS 인터럽트사용 가능 (int 0x10/0x13/0x15)사용 불가. 커널이 직접 드라이버를 가져야 함
보호·페이징없음권한 단계(ring 0~3), 페이징 가능
이 프로젝트에서bootsect.s, setup.shead.s, main.c 이후 전부

세그먼트:오프셋 계산

리얼모드의 선형 주소는 cs*16 + ip입니다. gdb의 $pc는 ip만 보여주므로 0x104처럼 작게 보입니다.

예: 9020:0104 → 0x90200 + 0x104 = 0x90304. setup의 jmpi 0,8이 있는 실제 주소입니다.

BIOS 인터럽트와 부팅 적재

디스크 읽기(int 0x13)는 BIOS가 리얼모드용으로 제공합니다. 보호모드에서는 BIOS 코드를 그대로 호출할 수 없으므로 적재는 반드시 전환 전에 끝냅니다. 전환 뒤의 디스크 접근은 커널의 hd.c, floppy.c가 맡습니다.

GDT와 셀렉터

보호모드에서 cs, ds 같은 값은 주소가 아니라 GDT 항목 번호입니다. setup의 GDT는 널(0x00), 코드(0x08), 데이터(0x10) 세 개이고, 둘 다 base=0, limit=8MB, 32비트입니다. 그래서 선형 주소 = 오프셋이 되어 단순합니다. jmpi 0,8의 8이 코드 셀렉터입니다.

PE 비트와 far jump

CR0의 PE 비트를 켜면 보호모드가 시작되지만 CS의 캐시된 값은 그대로입니다. far jump로 CS를 새 셀렉터로 다시 읽어야 32비트 코드 세그먼트가 적용됩니다. 그래서 lmsw ax 바로 뒤에 jmpi가 옵니다. 원본은 mov cr0,eax 대신 286 시절 명령인 lmsw(CR0 하위 16비트 쓰기)를 씁니다.

A20과 PIC

A20: 옛 8086 호환을 위해 막혀 있는 21번째 주소선입니다. 열지 않으면 1MB 위 메모리가 0번지로 되돌아옵니다. 원본은 8042 키보드 컨트롤러로 엽니다. PIC 재설정: IRQ 번호가 CPU 예외 번호와 겹치지 않도록 0x20번부터 쓰게 옮깁니다.

페이징 (head에서)

pg0~pg3 4개 페이지 테이블이 0~16MB를 가상=물리로 1:1 매핑합니다. cr3에 pg_dir(주소 0)를 넣고 CR0.PG를 켜면 켜집니다. 페이지 디렉터리가 주소 0에 있는 건, 이미 쓸모없어진 head 앞부분 코드 자리를 재활용하기 때문입니다.

어셈블러가 두 종류인 이유

bootsect.s, setup.s는 1991년 원본 그대로 as86 문법(mov ax,#BOOTSEG, ! 주석)이고 as86 -0(8086, 16비트)로 어셈블합니다. ld86가 32바이트 minix 헤더가 붙은 파일을 만들고, 원본 tools/build.c가 헤더를 떼고 bootsect(512B) + setup(4섹터) + system을 이어 붙여 Image를 만듭니다. head.s, system_call.s 등 커널 쪽은 GNU as(AT&T 문법, as --32)로 32비트 ELF를 만듭니다. 원본 Linux 0.11도 같은 구성이었습니다(원본은 ELF가 아니라 a.out). a.out 시절 C 심볼에는 _가 붙었기 때문에(main → _main) 원본 .s 파일은 _main, _schedule처럼 씁니다. 지금은 gcc에 -fleading-underscore를 줘서 같은 이름을 만들고 원본 .s를 그대로 씁니다. gdb에서는 디버그 정보 덕에 hbreak main처럼 _ 없이 씁니다.

어셈블리와 기계어

16/32비트는 어셈블러에게 하는 지시이고 결과 바이너리에는 남지 않습니다. 같은 mov ax,#0x07c0이 16비트로는 B8 C0 07, 32비트 코드에서는 66 B8 C0 07입니다(0x66은 operand 크기를 뒤집는 prefix). CPU는 바이트만 보고, 해석 방식은 현재 모드가 정합니다. 어셈블러 설정과 CPU의 실제 모드가 어긋나면 명령 길이가 달라져 이후 바이트가 전부 엉뚱하게 읽히고, 에러도 없이 조용히 오동작합니다.

6. 질문과 답

작업하면서 나온 질문을 정리했습니다.

Q1. d16으로 디코드하는데, 기계어와 어셈블리어를 어떻게 구별하나요?

구별하지 않습니다. 기계어에는 모드 표시가 없고, 어셈블리는 어셈블 단계에서 이미 사라집니다. d16은 커널 코드가 아니라 gdb 안에서만 도는 디버깅 명령(scripts/d16.py)입니다.

  • QEMU 메모리에서 현재 위치의 바이트를 읽어 objdump -m i8086에 넘겨 16비트로 역어셈블합니다.
  • 이렇게 우회하는 이유는 gdb 9.x가 set architecture i8086 뒤에도 x/i를 32비트로 해석하기 때문입니다. layout asm에 add BYTE PTR [eax],al만 잔뜩 보이는 게 그 증상입니다.
  • 모드 선택은 CPU 상태(CR0.PE와 CS)로 합니다. 자동입니다.
Q2. 지금 보고 있는 명령이 소스의 어디인지 모르겠어요.

output/bootsect.elf는 완성 바이너리를 ELF로 감싼 것뿐이라 디버그 정보(라인 테이블)가 없습니다. 그래서 gdb에 in ?? ()만 나옵니다.

대신 as86 -l로 만든 리스팅(output/bootsect.lst, output/setup.lst)에서 줄번호 / 오프셋 / 기계어 / 소스가 1:1로 대응합니다. 주소는 아래 표대로 구합니다. d16이 이 표를 자동으로 적용해 ; bootsect.s:47 mov ax,#BOOTSEG처럼 붙여 줍니다.

Q3. 보호모드로 바뀌면 32비트로 읽어서 d16으로는 안 될 텐데, 어떻게 확인하죠?

그래서 d16이 CR0.PE=1 이고 CS가 GDT 셀렉터(작은 값)일 때를 보호모드로 판단해, set architecture i386와 symbol-file tools/system으로 자동 전환하고 기본 x/i를 씁니다. stepi만 눌러도 전환이 따라갑니다.

CS까지 보는 이유: lmsw ax와 jmpi 0,8 사이는 PE=1이지만 CS가 아직 리얼모드 값이라 16비트이기 때문입니다. 전환 뒤에는 list로 head.s, main.c 소스 줄까지 보입니다.

Q4. 부트로더가 보호모드까지 진입하나요? OS를 램에 올리는 건 보호모드 진입 후인가요?

보호모드 진입은 부트로더(setup)의 마지막 일이 맞습니다. 하지만 순서는 반대입니다. 디스크에서 RAM으로 올리는 일이 먼저, 리얼모드에서 BIOS로 끝납니다. 그 뒤 setup이 모드를 바꿉니다.

  • 부트로더의 범위: bootsect + setup. 임무는 "커널을 RAM에 올리고, 보호모드를 켜고, 진입점으로 점프"입니다.
  • head.s부터는 커널(system)입니다. jmpi 0,8 한 줄이 경계입니다.
  • 보호모드 이후의 디스크 접근(루트 파일시스템 등)은 커널 드라이버가 합니다.
Q5. si로 따라가다 귀찮아서 continue 했더니 Kernel panic: Unable to mount root가 났어요. 부트로더를 못 빠져나온 건가요?

아닙니다. Loading system ... 다음에 커널 메시지가 나왔다면 bootsect → setup → head → main까지 다 넘어간 것입니다. 루트 파일시스템이 있는 하드디스크 이미지가 QEMU에 안 붙어 있어서 루트 마운트(위 16번 단계)에서 멈춘 것입니다. 지금 scripts/qemu-debug.sh boot는 output/hdc-0.11.img가 있으면 같이 붙이므로 continue로 쉘까지 갑니다.

continue는 다음 중단점까지 실행하는 명령이라 써도 됩니다. si 50000 대신 보고 싶은 지점에 hbreak를 걸고 continue 하세요(아래 표).

Q6. VSCode로는 main까지 되는데 부트로더는 왜 안 되나요?

VSCode(cppdbg)는 bootsect 구간에서 gdb의 정지 상태를 "실행 중"으로 인식해 stepi가 안 됩니다. 그래서 WSL 터미널 두 개(bootloader_terminal1.sh: QEMU, bootloader_terminal2.sh: gdb)로 직접 디버깅합니다. 보호모드 이후(startup_32~main)는 VSCode 설정으로도 됩니다.

Q7. 원본 소스는 왜 그대로 빌드되지 않나요? 무엇을 고쳤나요?

원본은 1991년 gcc 1.x와 a.out 형식용이고, 빌드 환경(Ubuntu 14.04)에는 gcc 4.8밖에 없습니다. 최적화를 하려고 고친 게 아니라, 지금 컴파일러로 빌드하고 바르게 동작하게 하는 데 꼭 필요한 것만 고쳤습니다. 원본과 다른 파일은 26개이고 diff -r linux-0.11-original . -x linux-0.11-original -x .git로 전부 볼 수 있습니다.

  • 컴파일 에러: 인라인 asm에서 입력으로 준 레지스터를 clobber 목록에도 적는 것(gcc 3 이후 impossible constraints), 캐스트에 대입, #elif만 쓰기, xorl %al,%al, .align 3(a.out에선 2³바이트, ELF에선 3바이트), 바이트 값에 "r" 제약(%sil이 나옴).
  • 에러는 없지만 잘못 동작: gcc 4.8은 "함수 경계에서 방향 플래그 DF=0"을 가정하고 구조체 복사를 rep movsl로 만듭니다. 원본은 std를 쓴 뒤 DF를 끄지 않아서, fork의 *p = *current가 get_free_page() 직후 거꾸로 복사됐습니다. task 1의 priority가 0이 되어 스케줄러가 init을 영영 고르지 못했습니다. std를 쓰는 4곳 끝에 cld를 넣어 해결했습니다.
  • a.out 심볼: 원본 .s는 C 심볼을 _main처럼 부릅니다. 소스를 고치는 대신 gcc에 -fleading-underscore를 줬습니다.
  • 환경 차이: QEMU IDE 호환(hd.c 2줄, 15단계 참고), Windows 드라이브의 대소문자 무시(keyboard.S 빌드 규칙), 원본 build.c를 고치지 않고 쓰기 위한 컴파일 옵션(-m32)과 Makefile 연결.
Q8. 커널이 127KB에서 107KB로 줄었는데, 동작이 달라진 건가요?

아닙니다. 이전에 쓰던 버전은 컴파일 옵션에 -O(최적화)가 빠져 있었고, 지금은 원본 Makefile대로 -O를 씁니다. 같은 C 코드를 원본과 같은 최적화 수준으로 컴파일해서 작아진 것입니다. -O는 fork/pause 인라인에 필요하기도 합니다(14단계).

대신 gdb에서 일부 변수가 <optimized out>으로 보이거나 next로 진행할 때 줄이 앞뒤로 튈 수 있습니다. 최적화된 코드라서 생기는 정상 동작입니다.

Q9. 키보드 배열은 왜 바꿨나요?

원본 기본값은 핀란드식(include/linux/config.h의 KBD_FINNISH)이라, 한국/US 키보드로 QEMU 쉘에 칠 때 /가 -, -가 +, >가 :로 들어갑니다. 원본에 이미 있는 KBD_US를 켜고 KBD_FINNISH를 껐습니다. keyboard.S는 켜 둔 배열의 표 하나만 어셈블하므로 커널 크기는 같고, 둘 다 켜면 먼저 검사하는 핀란드식이 쓰입니다.

저장소 루트에서 실행합니다. 처음 한 번은 ./build.sh와 ./build.sh boot로 Image와 리스팅을 만듭니다.

# 터미널 2: gdb 접속. 0x7c00에서 멈춘다. 멈출 때마다 현재 명령과 소스 줄이 자동 출력된다
./bootloader_terminal2.sh
중단점위치 (원본 소스)

주소는 output/*.lst의 오프셋(둘째 칸)에 로드 위치를 더한 값입니다. 소스를 고치면 바뀌므로 리스팅에서 다시 확인합니다.

setup 구간(cs=0x9020)에서는 gdb가 $pc를 ip(예: 0x104)로 보기 때문에, 선형 주소로 건 hbreak에 멈춰도 Breakpoint N 대신 Program received signal SIGTRAP으로 표시됩니다. 정상 동작입니다.
